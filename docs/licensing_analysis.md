## 1. 현황 (실측)

- `LICENSE`: 순수 **MIT** 단일. 저작권자 1인(호시 <jahyag@gmail.com>), org `sjpupro-lab`.
- `AUTHORS`: 기여자 1인. → **현재까지는 단일 저작권자**라 재라이선싱·듀얼 라이선싱에
  제3자 동의가 필요 없다(중요 — 아래 §7 CLA 참고).
- 소스 헤더 전반: `Licensed under the MIT License. See LICENSE.`
- 배포 형태: 정적 라이브러리 `libbcb.a`(+ 임베디드 C API). 동적 라이브러리는 아직 없음.
- `CONTRIBUTING` / `CLA` / `DCO` 없음.

### 핵심 리스크

MIT 하에서는 **누구나 합법적으로 코드를 그대로 가져다 상업 제품에 넣고 재판매**할 수
있다. 출처 표기(저작권 고지 유지) 외에는 의무가 없다. 상업화 관점에서 이것이 가장 큰
법적 노출이다.

### 되돌릴 수 없는 제약 (가장 중요한 정직한 한계)

**이미 MIT 로 공개된 커밋은 영구히 MIT 다.** 라이선스를 바꿔도 *소급 적용되지 않는다*.
즉 누군가 마지막 MIT 커밋(또는 그 이전)을 fork 하면, 그 시점의 코드를 영원히 MIT 로
쓸 수 있다. **듀얼 라이선스는 오직 *앞으로의* 버전에만 보호를 건다.**

따라서 라이선스 변경의 실효성은 "변경 이후 버전이 이전 MIT 버전 대비 충분한 가치를
더하는가"에 달려 있다. 다행히 BCB 는 활발히 개발 중(v0→v6, API v0.2, fuzzing/검증
강화)이라 미래 버전의 가치 우위를 만들기 좋은 위치다. 하지만 이 한계는 영업·법무에
반드시 정직하게 공유해야 한다.

## 2. 듀얼 라이선스 설계 개요

```
                ┌─────────────────────────────────────────┐
                │                BCB 코드                  │
                └─────────────────────────────────────────┘
                       │                         │
        (a) 오픈/소스공개 트랙          (b) 상업 트랙 (Commercial)
   비상업·연구·평가·커뮤니티용         기업의 폐쇄형/프로덕션 제품용
   가치 보호형 라이선스               별도 상용 라이선스 (연간 구독 + 지원)
   ── AGPLv3 / BUSL-1.1 / PolyForm    ── LICENSE-COMMERCIAL
```

- **하나의 코드베이스**를 두 라이선스로 동시에 제공한다("sell exceptions" 모델;
  MySQL·Qt·iText 등이 쓰는 전형적 구조).
- 단일 저작권자라서 가능하다. 고객은 오픈 트랙 의무를 피하려고 상업 라이선스를 산다.
- 오픈 트랙이 **충분히 "불편"**해야(=프로덕션/폐쇄 제품에 쓰기 어려워야) 상업 트랙이
  팔린다. 이 "불편함"의 성격이 아래 후보별로 다르다.

## 3. 오픈/소스공개 트랙 후보 비교

### 정적 라이브러리(.a)에서 "전파 범위"가 왜 핵심인가

BCB 는 고객 제품에 **정적 링크(.a)**되어 들어간다. 라이선스마다 의무가 *무엇을 계기로*
발생하는지가 다르다:

- **Copyleft(AGPL/GPL)** → 계기는 **"파생물/결합물 생성"**. 정적 링크하면 결합 바이너리
  전체가 파생물로 간주되어 copyleft 가 *전파*된다. (FSF 해석상 동적 링크도 결합물로 본다.)
- **BUSL** → 계기는 **"프로덕션 사용"**. 링크 방식과 무관. 파생물 여부가 아니라 *용도*.
- **PolyForm Noncommercial** → 계기는 **"상업적 사용"**. 역시 링크 방식 무관, *목적* 기준.

| 항목 | **AGPLv3** | **BUSL-1.1** | **PolyForm Noncommercial 1.0.0** |
|---|---|---|---|
| 분류 | OSI 승인 **오픈소스** (자유 소프트웨어) | **소스 공개**(OSI 비승인) | **소스 공개**(OSI 비승인) |
| 허용 | 모든 사용. 단 배포/네트워크 제공 시 copyleft 의무 | **프로덕션 외** 모든 사용(개발·평가·테스트·내부 PoC 자유) | **비상업** 사용만(연구·교육·개인·비영리) |
| 제한의 계기 | 파생물 배포 + **네트워크 제공(§13)** | **프로덕션 사용** | **상업적 사용** |
| 정적 .a 전파 | 결합 바이너리 전체가 AGPL → 배포/SaaS 시 **전체 소스 공개 의무** | 전파 개념 없음. "프로덕션이냐"만 본다 | 전파 개념 없음. "상업이냐"만 본다 |
| 시한부 개방 | 없음(영구 AGPL) | **Change Date(≤4년) 후 지정 라이선스(예 Apache-2.0)로 자동 전환** | 없음(영구) |
| 상업 전환 레버 | 강함: 폐쇄 제품은 소스 공개 불가 → 상업 라이선스 구매 | 강함·명확: "프로덕션 쓰려면 구매" | 강함·단순: "상업이면 구매" |
| 커뮤니티 신뢰 | 높음(진짜 오픈소스, OSI) | 중간(시한부 개방이 안전판) | 낮음~중간(영구 비개방) |
| BCB 적합성 메모 | 임베디드 코덱엔 §13(네트워크)이 잘 안 걸릴 수 있으나, 배포/파생물 레버는 견고 | 라이브러리에 가장 *명확한* 경계(파생물 논쟁 회피) | 가장 단순·강력하나 기업 내부 평가까지 막아 영업 깔때기 마찰 |

### 후보별 장단점 (BCB 관점)

**AGPLv3**
- ✅ OSI 승인 오픈소스 → "오픈소스 프로젝트" 브랜딩·커뮤니티 유지. 검증된 듀얼 모델.
- ✅ 정적 링크 = 파생물 → 폐쇄형 제품은 소스 공개 의무 → 상업 라이선스 구매 유인(레버).
- ⚠️ *라이브러리*에 AGPL 은 공격적이다. 정당한 OSS 사용자도 자기 제품을 AGPL 로
  공개해야 하므로(linking exception 없으면) 채택을 꺼릴 수 있다.
- ⚠️ "내 제품이 파생물인가?"라는 **파생물 경계 불확실성**이 기업 법무를 긴장시킨다.
  (이 불확실성이 곧 구매 동기가 되기도 한다 — 양날의 검.)
- ⚠️ §13 네트워크 조항은 *서비스*용이라, 폐쇄 펌웨어/온디바이스 임베딩엔 덜 자연스럽다.

**BUSL-1.1**
- ✅ 라이브러리에 **가장 깔끔한 경계**: "프로덕션 사용이냐"만 본다. 정적/동적 링크,
  파생물 여부 논쟁 불필요 → 기업 법무가 이해·승인하기 쉽다.
- ✅ 개발·평가·내부 PoC 가 자유 → **영업 깔때기 마찰이 가장 적다**(개발자가 회사에서
  맘껏 시험 → 프로덕션 직전에 구매).
- ✅ **Change Date(보통 1~3년) 후 Apache-2.0 등으로 자동 전환** → 커뮤니티 신뢰·안전판.
- ⚠️ OSI "오픈소스"가 아니다(소스 공개일 뿐). "오픈소스" 브랜딩을 원하면 부적합.
- ⚠️ 임베디드 코덱에서 "프로덕션 사용"의 정의를 *Additional Use Grant* 로 명확히
  적어줘야 한다(예: "출하 제품/유료 서비스에 포함 = 프로덕션").

**PolyForm Noncommercial 1.0.0**
- ✅ 가장 단순·평이한 문구. "비상업이면 자유, 상업이면 구매" — 보호가 가장 강하고 명확.
- ✅ 연구·교육·개인 사용자에게 친화적.
- ⚠️ "비상업"이 BUSL 의 "비프로덕션"보다 **좁다**. 기업 개발자가 *업무 중 평가*만 해도
  상업 사용에 해당할 소지 → 영업 깔때기 초입에서 마찰.
- ⚠️ 영구 비개방(Change Date 없음) → 커뮤니티 신뢰 측면 약함.
- ⚠️ OSI 오픈소스 아님.

## 4. 추천안

### 1순위 추천: **BUSL-1.1 (오픈/소스공개 트랙) + 별도 상업 라이선스 (상업 트랙)**

**근거 (BCB 의 특성에 맞춤):**

1. **임베디드 정적 라이브러리에는 "용도" 경계가 "파생물" 경계보다 압도적으로 명확하다.**
   BCB 는 .a 로 고객 제품에 정적 링크된다. AGPL 을 쓰면 "이 결합 바이너리가 파생물인가,
   그래서 전체를 공개해야 하나"라는 *정적 링크 copyleft 전파* 논쟁이 매 고객마다 생긴다.
   이는 기업 법무가 가장 싫어하는 불확실성이다. BUSL 은 그 논쟁을 통째로 우회한다 —
   "프로덕션에 쓰면 상업 라이선스, 아니면 자유". 영업·법무 양쪽이 한 문장으로 이해한다.

2. **영업 깔때기 마찰 최소화.** B2B 고객은 "내 데이터로 먼저 재현·평가"한 뒤 구매한다
   (벤치마크 신뢰가 0순위인 이유와 같다). BUSL 은 개발·평가·내부 PoC 를 자유롭게
   허용하므로, 평가 단계에서 라이선스 장벽이 없다. 프로덕션 진입 직전에 자연스럽게
   상업 라이선스로 전환된다.

3. **Change Date 안전판이 커뮤니티 신뢰를 산다.** 각 릴리스가 N년 뒤 Apache-2.0 으로
   자동 전환되도록 설정하면, "언젠가는 오픈된다"는 신뢰를 주면서도 *현재* 버전의 상업
   가치는 보호한다. (§1 의 "이미 MIT 인 과거 커밋" 문제와 별개로, 미래 버전에 시한부
   보호를 거는 합리적 타협.)

**제안 파라미터 (변호사 검토 후 확정):**
- *Change Date*: 각 릴리스 배포일 + **3년** (CockroachDB/Sentry 류 관례. 1~4년 범위).
- *Change License*: **Apache-2.0** (특허 grant 포함 → 전환 후 진짜 오픈소스).
- *Additional Use Grant*: "프로덕션이 아닌 모든 사용(개발·평가·테스트·내부 비프로덕션
  PoC·연구·교육)을 허용. *프로덕션 사용*은 출하/판매되는 제품에 BCB 를 포함하거나
  유료·외부 제공 서비스의 운영에 사용하는 것을 말하며 상업 라이선스를 요한다." (문구 확정 필요)

### 2순위(차선): **AGPLv3 + 상업 예외(commercial exception)**

"OSI 승인 **오픈소스**" 브랜딩이 전략적으로 중요하다면 AGPLv3 가 1순위가 된다. 검증된
"sell exceptions" 모델이고, 정적 링크 copyleft 가 강력한 구매 레버다. 대신 §3 의 파생물
경계 불확실성과 라이브러리-AGPL 의 공격성을 감수해야 한다. **선택은 "오픈소스 OSI
브랜딩이 필수인가" vs "임베디드 라이브러리에 깔끔·집행가능한 경계가 우선인가"로 갈린다.**

### 비추천(이 시점): PolyForm Noncommercial

보호는 가장 강하지만 "비상업" 경계가 기업 평가 단계까지 막아 B2B 영업 깔때기를 좁힌다.
순수 연구/학술 배포가 주목적이라면 그때 재검토.

## 5. 정적 .a Copyleft 전파 — 고객에게 어떤 의미인가 (필수 설명)

(AGPLv3 를 택할 경우의 시나리오. BUSL/PolyForm 은 §3 대로 "전파" 개념이 없고 *용도*만 본다.)

- **정적 링크(.a)**: 고객이 `libbcb.a` 를 자기 애플리케이션에 정적 링크하면, 결과
  바이너리는 BCB 와 고객 코드의 **결합물(combined work)**이다. AGPLv3 에는 별도
  linking exception 이 없으므로, 이 결합물 전체가 AGPLv3 의 적용을 받는다.
- **배포 시**: 그 바이너리(예: 펌웨어 이미지, 설치형 제품)를 배포하면, AGPLv3 는 **결합물
  전체의 완전한 대응 소스(complete corresponding source)**를 동일 라이선스로 제공할 의무를
  지운다. → 폐쇄형 상용 제품에는 사실상 불가능 → **상업 라이선스 구매**.
- **네트워크 제공 시(§13)**: 바이너리를 배포하지 않고 SaaS 백엔드에서만 돌려도, AGPLv3
  §13 은 그 서비스 사용자에게 소스 제공 의무를 지운다(GPL 대비 AGPL 의 핵심 차이). 단,
  *온디바이스 임베디드*(네트워크로 사용자와 상호작용 안 함)에는 §13 이 안 걸릴 수 있어,
  이 경우 레버는 배포/파생물 조항이 된다.
- **동적 링크(.so, 향후 도입 예정)**: FSF 해석상 동적 링크도 결합물로 본다. 즉 .a 든 .so 든
  copyleft 전파를 트리거한다(이견 있는 영역 — 변호사 검토 필수).

> 요약: AGPL 의 보호력은 "정적 링크 = 파생물 = 전체 공개 의무"라는 전파에서 나온다.
> 동시에 이 전파의 *경계 불확실성*이 정당한 사용자를 위축시키는 비용이다. BUSL/PolyForm 은
> 이 전파·불확실성을 "용도(프로덕션/상업)" 한 줄로 대체한다 — 그래서 본 리포트는 임베디드
> 라이브러리인 BCB 에 BUSL-1.1 을 1순위로 추천한다.

## 6. 상업 트랙 (Commercial License) 개요

기업 고객용 별도 상용 라이선스. 오픈 트랙 의무(프로덕션 제한 또는 copyleft)를 면제하는
대가로 연간 구독 + 지원을 제공한다. `LICENSE-COMMERCIAL` 초안의 골자(변호사 검토 필요):

- **부여(Grant)**: 오픈 트랙 의무 없이 BCB 를 고객 제품에 포함·배포·프로덕션 사용할 수
  있는 비독점·양도불가 라이선스.
- **범위(Scope)**: 좌석/제품/배포량 등 과금 단위 정의. (예: 제품 라인당, 또는 디바이스
  수량 티어, 또는 사이트 라이선스.)
- **기간/구독(Term)**: 연간 구독. 구독 중 출시한 버전은 영구 사용 가능(perpetual for
  versions released during the term) 옵션 검토.
- **지원/유지보수(Support)**: SLA, 버전 업데이트, 보안 패치 우선 제공.
- **무결성/보안 약정**: SBOM·서명 릴리스 제공(task 8 연계 — 엔터프라이즈 요구).
- **보증·책임(Warranty/Liability)**: 한정 보증 + 책임 한도. (오픈 트랙의 "AS IS" 와 차별.)
- **상표·감사·종료 조항** 등 표준 상용 조항.

영업 흐름: 오픈 트랙(BUSL)으로 평가 → 프로덕션 직전 `commercial@…` 문의 → 상업 계약.

## 7. 기여자 라이선스 동의 (CLA vs DCO) — 판단

**결론: 듀얼 라이선스를 하려면 CLA 가 필요하다. DCO 만으로는 불충분하다.**

- **DCO (Developer Certificate of Origin)**: 기여자가 "이 코드를 프로젝트 라이선스로
  제출할 권리가 있다"고 *증명*만 한다. 메인테이너에게 **재라이선싱 권한을 주지 않는다.**
  → 외부 기여 코드를 상업 라이선스로 다시 팔 권리가 생기지 않음 → 듀얼 모델에 부적합.
- **CLA (Contributor License Agreement)**: 기여자가 메인테이너에게 **넓은 라이선스(또는
  저작권 양도)**를 부여 → 메인테이너가 그 기여분을 오픈+상업 양쪽으로 배포할 권리 확보.
  → **듀얼 라이선스의 전제조건.**

**권고:**
1. **지금**: 저작권자 1인이라 과거 기여 문제 없음. **외부 PR 을 받기 전에** 경량 CLA 도입.
   (예: Apache 스타일 ICLA, 또는 inbound=outbound + 상업 재배포 권한을 명시한 단문 CLA.
   GitHub 의 CLA Assistant 봇으로 PR 시 자동 서명 수집.)
2. CLA 채택 시 `CONTRIBUTING.md`(task 6)에 서명 절차를 명시.

## 8. 채택 시 변경할 파일 (승인 후 진행)

> 아래는 *추천안(BUSL-1.1)* 채택을 가정한 작업 목록이다. 아직 **착수하지 않았다.**

1. `LICENSE` — MIT → 채워진 **BUSL-1.1 템플릿**(Licensor, Licensed Work=BCB, Additional
   Use Grant, Change Date, Change License=Apache-2.0). *기존 MIT 의 과거 적용은 소급
   무효화 불가 — §1 한계 명시.*
2. `LICENSE-COMMERCIAL` — §6 골자의 상용 라이선스 초안(변호사 검토 전 *초안* 표기).
3. `COMMERCIAL.md` 또는 README — 상업 문의 연락처/절차 안내.
4. `README.md` "License" 섹션(193–195줄) 갱신: 듀얼 라이선스 설명 + 두 트랙 안내.
5. 소스 헤더 SPDX 전환: `Licensed under the MIT License.` → 적절한 SPDX 식별자
   (`SPDX-License-Identifier: BUSL-1.1`) 일괄 갱신. (※ 과거 태그/릴리스 헤더는 그대로 둠.)
6. `CLA.md` + CLA Assistant 설정(§7). `CONTRIBUTING.md`(task 6)와 연계.
7. 변경 시점을 명확히 하는 `CHANGELOG`(task 6) 항목 — "vX.Y.Z 부터 BUSL-1.1".

## 9. 다음 단계 — 승인 요청

저작권자(호시)의 결정이 필요한 사항:

1. **트랙 (a) 라이선스 선택**: ☐ BUSL-1.1(추천) ☐ AGPLv3 ☐ PolyForm Noncommercial ☐ 기타
2. (BUSL 선택 시) **Change Date 기간**(예: 3년)과 **Change License**(예: Apache-2.0) 확정.
3. **상업 트랙 과금 모델** 방향(제품당 / 디바이스 티어 / 사이트 라이선스 등).
4. **CLA 도입 시점**(권고: 외부 PR 수령 전).
5. **변호사 검토** 일정 — 채택 *전* 필수.

승인이 떨어지면 §8 의 파일들을 작성한다(상용 라이선스/실제 LICENSE 본문은 변호사 검토
플래그를 단 초안으로 제출).
